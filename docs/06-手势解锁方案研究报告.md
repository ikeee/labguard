# 断网遮罩「按键手势解锁」方案研究报告

> 需求：去掉密码框，老师按 **`Pause/Break` 激活 → `↑↑↓↓←→←→`** 解锁。
> 研究日期：2026-09-30 · 环境：本机（真实噢易 VOI 机房学生机，LabGuard 已正式安装到 `C:\Program Files\LabGuard`）
> 方法：写一个**独立的低级键盘钩子探针**（`WH_KEYBOARD_LL`，回调内 `return 1` 吞键，与遮罩完全同模型）在本机实测，而不是只做纸面推演。

> **实现状态：已于 v0.06 落地**（`Interop/UnlockGesture` + 第 2 组 5 项配置 + `--unlock-drill --gesture`）。
> 真机演练验证结果见 §9.1，与本文的预判一致。本文保留作为**论证与取舍的记录**。

---

## 1. 结论速览

| 维度 | 结论 |
|---|---|
| **技术上是否可行** | ✅ **完全可行**。Pause 与四个方向键都能被现有钩子稳定识别 |
| **比现在的方案更好还是更差** | **可靠性明显更好，保密性明显更差**（详见 §5、§6） |
| **最大的红利** | 可以**全程不解除 `BlockInput` 硬锁**（已实测证实）→ 现在这条通道上的 Bug 会被一次性根除 |
| **必须处理的坑** | ① 长按 autorepeat **必须去重**；② Pause 键在部分键盘上没有；③ Ctrl+Pause **无法**与 Pause 区分 |
| **最大的风险** | `↑↑↓↓←→←→` 是公开的 Konami Code，学生在旁边看一遍就会，**且不像密码那样可以更换** |
| **建议** | 做成**可配置项**，默认「手势 + 密码双通道」，由老师按机房情况切换；不要直接删掉密码通道 |

一句话：**这个想法的价值不在于"少输一次密码"，而在于它把解锁路径从「全局钩子 + 输入硬锁 + 模态密码框」三种机制交叉，压缩成了「单一钩子状态机」——而这恰好是近三轮 Bug 的共同根源。**

## 2. 实测方法与证据

探针是临时写的 `net48` 独立程序（`D:\MY-PROJECT\_keyprobe\`，**不在 labguard 仓库内**），核心结构与 LabGuard 现有钩子一致：

```csharp
_proc = Cb;                                              // 委托必须存活，否则被 GC
_hook = SetWindowsHookEx(13, _proc, GetModuleHandle(null), 0);
private static IntPtr Cb(int nCode, IntPtr wParam, IntPtr lParam) {
    if (nCode >= 0) { /* 读 vkCode / scanCode / flags / tick */ }
    return (IntPtr)1;                                    // 吞键——与遮罩完全同模型
}
```

原始记录见 `_keyprobe5.txt`（本文所有数据都来自它，可复核）。

| # | 测试项 | 实测结果 | 判断 |
|---|---|---|---|
| T1 | 单点 `Pause/Break` | `vk=0x13`，`keydown` + `keyup` **成对** | ✅ 可捕获 |
| T2 | `Ctrl + Pause` | 仍收到 **`vk=0x13`**（没有变成 `0x03 VK_CANCEL`） | ⚠️ 见 §5.3 |
| T3 | 四个方向键 | `↑=0x26 ↓=0x28 ←=0x25 →=0x27`，down/up 配对正常 | ✅ 可识别 |

| T5 | 正常连按两次 ↑（220ms） | 两组完整的 down/up，与 T4 **形态完全不同、可区分** | ✅ |

## 3. 为什么我说它比密码方案更可靠

现在这条解锁通道，最近三轮连续出问题，而且三个 Bug 的**根各不相同**：

| 期次 | 症状 | 根因 |
|---|---|---|
| 第一轮 | 五次 Esc 后密码框没在最前 | 模态框没有 owner / 不 TopMost，被 TopMost 全屏遮罩压住 |
| 第一轮 | 插回网线后遮罩消失但键鼠锁死 | 密码框"取消"分支无条件重新上锁，且定时器继续续心跳使看门狗失效 |
| 第二轮 | 五次 Esc 后**密码打不进去** | 在钩子回调里直接弹模态框 → 回调不返回 → 钩子链串行阻塞 → 所有按键被排队 |

它们的**共同根源**都是同一句话：**为了在"硬锁 + 全吞键"的状态下，给一个人造的输入框把字送进去，必须先临时拆掉一部分自己。**

而手势解锁**不需要任何输入框**。`§2` 的 T8 已经证明：**`BlockInput` 硬锁期间，钩子本身照样能收到 Pause 和方向键。** 于是：

- 不需要 `InputLock.Disengage()` → 没有"重新上锁"的时序问题
- 不需要 `_teacherDialogOpen` 放行钩子 → 钩子可以**全程保持全吞**
- 不需要 `TopMost` 对话框 → 没有任何窗口层级问题
- 不需要给密码框做焦点、owner、数值校验 → 模态框整套代码一次都不执行
- 不存在的第四个问题：学生不可能"看到"老师在输入什么（密码方案里老师是当面敲密码的）

**保留的一条规矩**：解锁成功那一刻仍要 `BeginInvoke` 回 UI 线程做收尾，不能在钩子回调里直接操作 UI——回调阻塞的机理没变，只是这次收尾动作很短。同时收尾仍要满足本项目的既有约定：**幂等、且由多条路径安全调用**。

## 4. 必须处理的三个坑

### 4.1 长按 autorepeat 必须去重（**不做就一定会出问题**）

T4 证明：长按 ↑ 不放会产生**连续的 `keydown` 而中间没有 `keyup`**。如果不处理，老师手一抖多按了半秒，`↑` 就会瞬间推进十几格，`↑↑↓↓←→←→` 直接被冲乱，**老师会以为机器坏了**。

正确的做法（也很简单）——要求同一个键**必须先抬起**才能再次计数：

```csharp
private int _heldVk;                     // 当前按住尚未抬起的键
// keydown:
if (vk == _heldVk) return swallowed;     // autorepeat，忽略
_heldVk = vk;
FeedGesture(vk);
// keyup:
if (vk == _heldVk) _heldVk = 0;
```

这同时满足两点：按下即响应（不必等抬起，手感跟得上），又天然过滤了 autorepeat（T4 的 5 次 down 只会算 1 次）。

### 4.2 Ctrl + Pause 无法与 Pause 区分

T2 显示 `Ctrl+Pause` 在低级钩子里仍是 `vk=0x13`，**不会**变成 `VK_CANCEL(0x03)`。

- **好处**：容错性强。老师手上有残留的 Ctrl/Shift 也能正常激活，不会莫名其妙失灵。
- **代价**：**做不出复合激活键**。"必须按住 Ctrl 再按 Pause"这种设计在低级钩子里区分不了（除非额外自己去记修饰键状态，徒增复杂度，不建议）。

结论：**激活键只能是单键**。

### 4.3 小键盘不算方向键

T6：小键盘 `8/2/4/6` 报的是 `VK_NUMPAD8/2/4/6`，与方向键不同。

建议**默认不接受**，理由：NumLock 开关状态会让同一颗键在两个语义间跳变，行为不可预测。如确有需要，做成单独的可选项，并且 NumLock 关闭时才生效。

## 5. 风险与权衡（决策真正要拍板的地方）

### 5.1 保密性：这是本方案唯一的实质性代价

| | 密码方案 | 手势方案 |
|---|---|---|
| 学生零知识时破解概率 | 6 位以上口令，可忽略 | 随机乱按：`(1/4)^8 ≈ 1/65536`，**可忽略** |
| 被目视偷学的概率 | 老师在学生面前敲，同样会泄露 | **同左**（没有变差） |
| 泄露后能否补救 | **能**——改密码即可 | **不能**——同一批机器全部失效，且要改配置重新下发 |
| 学生已是游戏玩家 | 几乎不知道 | Konami Code 是通用文化梗，**知道的人比例相当高** |

**结论**：泄露风险的**来源没变**（都是当面操作），但**爆炸半径和补救成本明显变差**。所以：

> 建议：**不要把密码通道删掉**，做成配置项二选一/双开，把这个取舍交给老师根据机房学生情况决定。

### 5.2 Pause 键可能不存在

104 键全尺寸键盘都有独立 `Pause/Break`；87 键、笔记本可能需要 `Fn` 组合甚至干脆没有。中小学教室机房基本是全尺寸键盘，风险偏低，但**值得把"激活键"做成可配置**：

| 备选 | 评价 |
|---|---|
| `Pause/Break`（默认） | 符合你的设想，位置独立不易误触 |
| `Scroll Lock` | 平时几乎不会被按到，位置也在右上角，适合做备用 |
| `Insert` / `Home` | 太常见，容易被学生瞎按命中，**不推荐** |

### 5.3 老师需要一点反馈，否则会以为机器坏了

按键手势的真正问题是：**按错了没有任何反馈**。老师按完 Pause、手忙脚乱按错一个方向键，屏幕毫无变化——他会重复尝试，甚至认为新功能坏了。

建议三个层次（都做成可配置）：

1. **默认完全静默**：黑屏上什么都不显示（最"保密"）
2. **失败时极轻反馈**（建议默认开）：序列输错或超时时，底部一行 12px 灰字闪一下 `手势未识别`，老师立刻知道要重来
3. **进度提示**（建议默认关）：右下角 8 个小点，按对一个亮一个。**这个学生也看得见**，等于公开演示，只在老师自己确认无旁观时才开

另外，整个过程需要一个**超时窗口**（建议 5 秒）：按完 Pause 后 5 秒内必须输完，超时自动重置，避免学生在旁边慢慢试。

## 6. 建议的具体设计（可直接照着实现）

### 6.1 新增配置项

放在 `NetworkSettings`（`src/LabGuard.Core/Config/GuardConfig.cs`，紧跟 `DisconnectMaskBackground` 之后）：

```csharp
/// <summary>老师解除遮罩的方式：Gesture=按键手势；Password=原 5×Esc+密码；Both=两者皆可（默认）。</summary>
public string TeacherUnlockMode { get; set; } = "Both";
/// <summary>手势激活键（单键）：Pause(默认) / ScrollLock。</summary>
public string UnlockGestureArmKey { get; set; } = "Pause";
/// <summary>解锁序列，逗号分隔；默认 ↑↑↓↓←→←→（U=上 D=下 L=左 R=右）。</summary>
public string UnlockGestureSequence { get; set; } = "U,U,D,D,L,R,L,R";
/// <summary>激活后必须在此秒数内输完，超时自动重置。</summary>
public int UnlockGestureWindowSeconds { get; set; } = 5;
/// <summary>是否显示序列进度点（学生也看得见，默认关）。</summary>
public bool UnlockGestureFeedback { get; set; } = false;
```

> ⚠️ **本项目硬约束**：自检 `[7] 设置项覆盖` 会反射核对——`GuardConfig` 里**每个叶子属性都必须在 `SettingsCatalog` 里有对应开关**，否则自检 FAIL。上面 5 个配置必须同时加 5 个 `Choice/Bool/Number` 条目，一个都不能少。

### 6.2 状态机（放在 `DisconnectMaskForm` 里，替换现有 `_escCount` 那套）

```csharp
// 状态：未激活 → 已激活（在窗口期内逐位匹配）→ 命中
private bool _armed;
private DateTime _armAt;
private int _seqPos;
private string[] _seq = { "U","U","D","D","L","R","L","R" };

private void FeedGesture(int vk)
{
    // 1) 还没激活 → 只有 Pause 能激活
    if (!_armed) {
        if (vk != VkPause) return;
        _armed = true; _armAt = DateTime.Now; _seqPos = 0;
        Log.Info("[遮罩] 手势已激活，等待 ↑↑↓↓←→←→");
        return;
    }
    // 2) 窗口超时 → 静默重置
    if ((DateTime.Now - _armAt).TotalSeconds > WindowSeconds) { ResetGesture(); return; }

    // 3) 方向键 → 逐位匹配
    string sym = SymbolOf(vk);                    // 0x26→U 0x28→D 0x25→L 0x27→R
    if (sym == null) return;                      // 其它键：忽略，不打断（宽容）
    if (sym == _seq[_seqPos]) {
        _seqPos++;
        if (_seqPos >= _seq.Length) {             // 命中
            ResetGesture();
            BeginInvoke(new Action(() => {        // 仍然要投递回 UI 线程收尾
                Log.Warn("老师用按键手势解除了断网遮罩");
                AutoClose("老师已用按键手势解除");
                try { _teacherUnlock?.Invoke(); } catch { }
            }));
        }
    } else {
        ResetGesture();                           // 走错一位，整段重来
        HintGestureFailed();                      // 极轻的失败反馈
    }
}
```

**关键点**：这段代码全程**不碰 `InputLock`、不碰钩子放行、不碰任何窗口层级**。这就是它可靠的根本原因。

### 6.3 `LockScreenForm` 是否同步

建议**同步**。它现在也要靠密码框解锁，能吃同样的红利。差异只有一处：它的钩子目前只吞 Win/Alt+Tab，普通键是放行的——改成手势后，除了四个方向键和激活键，其它键维持原策略即可。

## 8. 待真机人工复核（诚实标注）

自动化输入注入在本环境的局限（§2 标注）意味着，**以下几项只有人手动才能最终确认**：

1. 真人连按 `Pause → ↑↑↓↓←→←→` 能否一次命中（我只能证明每个单键都识别正确、且在硬锁下能送达）
2. 目标机房键盘是否有独立 `Pause/Break` 键
3. 输入节奏较快（约 150ms/键）时的手感与成功率
4. **长按去重的真机表现**：注入方式无法真实模拟"按住不放"（实测注入的连续 `keydown`
   会被系统补出配对的 `keyup`，所以去重分支压根没被触发）。该逻辑由自检 `[5.5]` 断言覆盖，
   但真机上老师手抖多按半秒会怎样，**必须人工试一次**。

### 9.2 一次值得记下的排查：负向用例"假 FAIL"

第一轮把四个用例串在一个脚本里跑时，B（错序列）和 C（不按激活键）都报了"居然解锁了"。
翻日志才看清是**测试方法的问题，不是代码问题**：

```
18:06:15.967  vk=0x13 → Armed pos=0     ← B 自己的 Pause
18:06:16.548  vk=0x28 → Mistake pos=0   ← B 的 ↓，判定正确并重置
   ……… 18 秒空白 ………
18:06:34.296  vk=0x13 → Armed           ← 凭空出现的 Pause + 完整正确序列
18:06:36.396  → Unlocked
```

中间那 18 秒空白里出现的，是**上一场景遗留的、被系统延迟送达的注入按键**
（这台机器会把合成输入延迟 12~19 秒，与早前记录一致）。B 自己的前两个键处理得完全正确。

**结论（已写进项目笔记）**：这台机器上做按键注入验证，**每个用例必须单独跑，且前面留 25~30 秒排空**，
否则上一轮的按键会迟到并污染下一轮的判定。
